# 交接校验与环境检查

## 执行入口与范围

从已安装的 production Skill 运行（需要其必需依赖 pipeline）：

```bash
python <production-dir>/scripts/validate_contract.py --project <project> --contract <handoff.json>
python <production-dir>/scripts/validate_contract.py --project <project> --contract <handoff.json> --preflight
```

第一条检查交接声明及引用证据。第二条另调用 pipeline `skills check`，核对安装内容与锁，确保 [routes.json](routes.json) 中选中路线的 Skills 均已安装，并核对外部能力。可选 Skill 仍须显式 update/install，不自动安装或切换路线。

输出区分 `validation_scope: inputs/assets/gate-review`，以及 `environment_checked`；`approval_granted` 始终为 false。只有输入契约通过不能代表资产已验收或 Gate 通过。普通探索可直接用通用 Skill，不伪造锁定上游满足本工具。

## 最小输入契约

```json
{
  "schema_version": 1,
  "repository_id": "my-production",
  "project_id": "my-story",
  "visual_profile": "shadow_puppet",
  "implementation_profile": "godot",
  "route_id": "flat-components",
  "asset_unit": "component-png",
  "hidden_region_policy": "concept-covered",
  "upstream": [
    {"path": "content/definition-v1.json", "version": "v1", "status": "locked", "sha256": "<SHA-256>"}
  ],
  "capabilities": {
    "Pillow": {"kind": "python-package", "distribution": "Pillow", "version": "<installed version>"}
  }
}
```

所有生产证据路径相对 `--project`，须存在且与 SHA-256 一致。JSON 上游还核对文件内 status/version；现有 Markdown 上游可直接引用，但其状态/version 由交接方声明，工具只核对文件哈希，不解析 Markdown frontmatter。需要机器保证状态时提供项目真实元数据的 JSON 适配记录，并保留原来源引用。

`route_id/asset_unit` 必须匹配路由表。`flat-components` 必须显式选择隐藏区策略；`inferred-repair` 还需 `policy_approval` 证据引用，其 JSON 绑定 repository_id/project_id/route_id/hidden_region_policy、upstream_sha256 数组、approved_by/approved_at。不能以严格概念覆盖契约静默启用推测补全。完整纸偶姿态使用 static-pose，不作为 component-png 交接。

## 外部能力与后端

`capabilities` 仅在 `--preflight` 时必查，每个选中路线的 external 名称分别提供：

| kind | 要求 | 检查边界 |
|---|---|---|
| executable | path、version | 文件存在且可执行；Blender >=4.5 路线还核对声明版本下限，不执行未知程序探测版本 |
| skill | 指向 SKILL.md 的 path、version | 外部技能文件存在；版本为项目记录值，调用前仍须读取接口 |
| python-package | distribution、version | 在运行本检查器的 Python 环境查询实际已安装版本；Pillow 对应 Pillow 分发 |
| service-evidence | evidence: path/sha256 | 项目已做的服务可用性检查 JSON，含 capability、available:true、checked_at、version；不连接服务重新测试 |

image generation 使用 service-evidence，sprite-gen 使用 skill，Blender 使用 executable。本机 capability path 可以是绝对路径，属于环境信息，不用作生产资产身份。服务记录时间和版本必须在制作前确认仍有效；本工具只验证其内容绑定，不保证远程服务当前可用或工具符合所有版本要求。

需要后端的路线（例如 clay-shot）或 Gate 送审必须提供：

```json
{
  "backend": {
    "entrypoint": "scripts/build.py",
    "validation_evidence": {"path": "audit/backend-check.json", "sha256": "<SHA-256>"}
  }
}
```

入口必须是项目真实文件，不得指向 skills/.agents/.claude 下的素材技能；检查器不运行后端。后端的实际支持范围、版本与验证结果由项目报告表达，证据存在不证明视觉或实现质量。

## 已验收素材与 Gate 送审

交付正式素材时增加 `assets_manifest: {path, sha256}`。该清单必须属于当前 repository/project，非空，文件完整，资产全部 locked，并通过 pipeline 的[严格资产与回执契约](../../ancient-tales-pipeline/references/资产校验契约.md)。工具原生 manifest 另行保留，不能拿它替代生产身份清单。

Gate 送审增加 `review` 对象，字段为：

- `gate`：gate-4 或 gate-5；`review_scope` 分别固定为 sample 或 full-film。gate-5 另需 locale，批准回执绑定同一 locale，不跨语言复用。
- `master_timeline` 与 `timeline`：有序 `{shot_id, frames}` 数组；fps 为正整数，total_frames 与本次 timeline 求和相等。
- sample 覆盖 3–5 个正式镜号，允许抽取非连续镜头；各镜时长须匹配 master。full-film 覆盖全部镜头且顺序与时长一致。
- `director_review_status/director_taste_review_status` 均为 pass。
- `master_evidence/output_evidence/approval_evidence`：各自的 path/sha256。

master_evidence 的 JSON 具有 status:locked、fps、timeline，并与 master_timeline 对账。output_evidence 指向实际被审输出；本工具验证字节，不解析视频证明帧数或视觉内容。approval_evidence 的 JSON 绑定 repository_id、project_id、gate、review_scope、timeline、fps、total_frames、master_sha256、output_sha256、approved_by、approved_at。改输出、范围或时长后，旧回执不得继续使用。

校验成功仅表示所给声明与证据一致。五个 Gate 的其他专业条件、完整播放、视觉判断、真实批准仍按总控执行；工具不推进阶段、不修改总控、不写新批准。
