# 资产校验契约

## 两种检查

```bash
python <pipeline-dir>/scripts/runtime.py assets verify --project <project>
python <pipeline-dir>/scripts/runtime.py assets validate --project <project>
```

`verify` 为兼容旧清单的基础检查：核对 repository/bucket、canonical POSIX 相对路径、文件大小和 SHA-256、URI 的命名空间及内容寻址、状态枚举。`project_id` 如存在，须匹配 `projects/<id>/` 路径；单项目工程把稳定 ID 写在 `assets.config.json` 的 `project_id`，从而验证其他资产根下的条目。资源条目若显式填写 `repository_id`，须与清单一致。push/pull 在任何网络操作前也检查基础元数据。

资产状态允许 `draft/review/approved/locked/blocked/needs-sync`；旧 `unreviewed` 保留为未审技术记录，不等于阶段 `draft`、用户批准或 Gate。需求表中的 planned/in-progress 等属于计划状态，不能当作资产批准状态。基础检查允许旧条目暂时缺少 asset_id/project_id/version；严格交接不得省略。

`validate` 在基础和文件检查之上，要求每条资产具有非空 `asset_id/project_id/version`，且身份版本不重复。`approved/locked` 条目须有以下字段：

```json
{
  "approval_receipt": "content/approvals/hero-v1.json",
  "approval_receipt_sha256": "<receipt SHA-256>"
}
```

回执格式：

```json
{
  "repository_id": "my-production",
  "project_id": "my-story",
  "asset_id": "hero-front",
  "version": "v1",
  "sha256": "<asset SHA-256>",
  "approved_by": "<actual confirmer>",
  "approved_at": "2026-11-05T10:00:00+08:00"
}
```

清单在顶层提供 `repository_id/bucket/assets`。每条的其他必需字段为 `path/sha256/size/status/uri`，URI 固定为 `hf://buckets/<bucket>/<repository_id>/objects/<sha256><lowercase-extension>`。业务 version 可为 `v1`，不要求等于哈希；未变记录重扫保持原样。回执与清单内已有 approved_by/approved_at 必须一致。

## 旧清单迁移

1. 先恢复文件，运行基础 `verify`；保存原身份、业务版本及批准原文。
2. 从项目当前事实补齐稳定 asset_id、project_id、version，不能只从故事名猜测归属；同资产多文件应使用可区分的文件 ID。
3. 依据真实历史确认建立 JSON 回执适配记录，绑定原被审哈希和确认者／时间；原批准文件保留，可在 JSON 增加来源引用。无法证明批准时不制造回执，保持未审或待审并处理下游绑定。
4. 记录回执文件哈希，运行严格 `validate`。按项目授权更新 Git 文本和清单；检查器不写回批准状态或替代资产上传。

服务端真实性、人工确认真实性和视觉质量不由哈希保证。检查器只核对当前记录及证据的完整性、一致性，不签发批准。`verify` 兼容性通过也不能替代正式交接的严格检查。
