# 资产所有权与追溯

## 职责

| 内容 | 权威位置 |
|---|---|
| 原始来源与可复用知识 | Obsidian 数据源，按来源库规则只读查询 |
| 共享 Skill、参考图片与动作库 | `lseyesl/skills` 的 Git，保持完整独立 |
| 剧本、分镜、提示词、契约、生产总控和批准回执 | 当前制作仓库 `projects/<project_id>/content/` 的 Git |
| 代码、配置和资产索引 | 当前制作仓库的 Git |
| 制作图片、音频、视频、模型和工程二进制 | 当前制作仓库明确配置的 HF bucket；索引记录可恢复身份 |

来源库和 Skill 库不参与 HF 同步。后端拥有实际消费的资源；跨项目共享必须有明确来源、权利和消费授权，不能因为故事相同就复用另一风格的活动素材。

## 稳定路径与状态协议

候选从生成开始使用版本化的稳定相对路径；`draft`、`review`、`approved`、`locked` 与 `needs-sync` 由 manifest 和回执表达，不靠搬动文件表达批准。改变已批准内容时新建版本并重新审阅，不覆盖旧版本。

### 正式引用字段

资源身份至少包括：

```yaml
repository_id: <production-repository>
project_id: <stable-project-id>
asset_id: <stable-asset-id>
version: <asset-version>
path: <repository-relative-path>
uri: hf://buckets/<owner>/<bucket>/<immutable-object-key>
sha256: <content-sha256>
size: <bytes>
status: review
```

### 候选提示词与正式绑定

代码 commit 用于追溯生成方式；它不能证明 HF 二进制存在。提示词正文在本项目 `content/视觉设计/提示词/` 维护，生成记录保存实际模型、seed、参数、提示词版本及输出哈希。候选提示词与正式提示词必须核对内容一致，禁止维护两个独立正文。

## 直接生成与恢复

1. 核对项目身份、风格、锁定上游及目标后端；缺少绑定时保持候选。
2. 生成到本项目稳定资源路径，执行确定性处理和专业验收，登记内容哈希。
3. 按仓库资产入口上传并回读验证。使用 `ancient-tales-pipeline` 的仓库先检查 `assets.config.json`，成功后才晋升 `assets.lock.json`。
4. 用户确认具体资产后，记录确认者、时间、被审哈希与状态；迁移、上传和自动测试不能代替批准。
5. 正式消费前核对索引、项目身份和实际文件，缺失或损坏即停止；下载先校验临时文件，再安装到相对路径。

已有 `assets/manifest.json` 或专用恢复脚本的仓库，先读取其当前入口和兼容规则。引入新工具不能覆盖或丢弃原资产索引。旧索引迁移必须另有映射及完整校验。

本地缺失不表示删除。`assets index` 应要求恢复缺失项；需要移除引用时显式 `assets forget --path ...`，已批准记录还需 `--allow-locked`。这些操作不删除本地文件或远端对象。

## 确认与提交

生产记录与批准回执在所有者制作仓库集中维护，不回写数据源。只在用户明确要求提交时创建 commit，精确暂存相关文本、代码和清单；媒体不进制作仓库 Git。批准与 Git 提交是不同事实，不以提交成功自动晋升资源，也不以一次未提交抹掉既有批准。

## 历史兼容

保留历史身份、哈希与批准事实，不因采用新工具改写其含义。旧路径只作证据，不能成为新的活动绑定。需要迁移旧资源时，先建立原路径、目标身份、哈希和状态的逐项映射，复用同哈希对象，验证恢复后再按授权移除旧副本。
